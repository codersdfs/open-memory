# ADR-0042: Project management rides the dimension

- **Status:** Accepted (2026-11-01) — the missing half of direction B: ADR-0020 gave every write a project, but nothing could list, create, rename or retire one. `stats.byProject` was the only enumeration, and a project's birth went unrecorded until its first real row.
- **Options:** a `projects` registry table (slug, created_at) that `list` UNIONs with the derived counts vs **derive everything from `memories.project`, and make `init` write one marker row** (chosen) vs no init at all — "a project appears on its first write".
- **Why not a registry table:** ADR-0020's whole point is that a project is a dimension and not an entity; a table makes it one, and then every answer has two sources — is a project the rows that carry it, or the row that reserved it? Listing would UNION, forgetting would have to keep the two in step mid-transaction, and an empty registered project would be a slug that means nothing to the brief, search or reconcile. The knowledge index needed a second table because links are edges between rows; a project needs no state a row cannot carry.
- **Why not no-init:** "it will exist after your first write" is honest and useless — the operator asking for project management is exactly the one who wants to see the project *now*, and `agent init` set the precedent that setup commands produce something visible. The marker is honest about what it is: one durable `decision` row, tagged `project:init`, in the shared layer (a project is a cross-agent concern), with the `note` as its text when one is given.
- **The marker must not cost the brief anything.** Written through `save()` it would be priced by curation (ADR-0040) and the write gate (ADR-0041), which read "Project X initialized." as scaffold — correctly. So `initProject` embeds and inserts directly, the same bypass `saveMany` and the knowledge sync take for deliberate writes, and `assembleBrief` skips the `project:init` tag: visibility in `project list` and `stats`, silence in the brief.
- **Rename can fold two projects, but never by accident.** The dimension is a plain column, so a rename is one `UPDATE memories SET project = ? WHERE project = ?` — tombstones included, because they are the audit trail of the project they documented. If the target slug already holds rows, that is a merge of two efforts' history: refused until `merge` is passed. The statement deliberately does not touch `updated_at`: a rename rewrites identity, not content, and bumping the column would reset the clock `purgeDeleted` judges tombstones by.
- **Forget is soft by default, detach is the explicit alternative.** `mode: "delete"` soft-deletes the project's live rows — every one restorable row by row, the same bargain a single `forget` strikes. `mode: "detach"` sets `project = NULL`, for rows that outlive the project they were filed under. A project with no live rows is not a project to the read surface, so both operations refuse an unknown slug rather than answering success for nothing.
- **The store methods are optional, like every other late capability.** `listProjects?`, `renameProject?`, `forgetProject?` on `VectorStore` keep a third-party store compiling. `MemoryService.listProjects` falls back to sweeping partitions and grouping in memory — correct at any size, only slower. Rename and forget have no row-wise fallback (`updateMeta` cannot change a project), so the service reports the missing capability instead of pretending.
- **Summaries count what a read can hand out:** `status = 'active' AND is_deleted = 0`, the population `list()` shows by default and the brief reads. A project whose rows are all archived honestly reads as empty here; `stats` (`byProject`, tombstones included) remains the operator's full view.

## Consequences

- `ProjectSummary { project, rows, byKind, lastActivityAt }` in `store/interface.ts`; both built-in stores implement the three methods (SQLite: one `GROUP BY project, kind` over `idx_memories_project_kind`, one `UPDATE` per operation, `vectors.clear()` after any that moved rows — the `prune` precedent for a rare sweep that changes membership without holding new vectors).
- Surfaces: `ai-memory project list|init|rename|forget` (alias `projects`), `memory_project` (MCP, `op` enum, the `memory_knowledge` shape), and `GET|POST /projects`, `POST /projects/:slug/rename`, `DELETE /projects/:slug?mode=` on the daemon.
- The brief's skip is a tag contract: any row tagged `project:init` is a management marker, wherever it came from.
- The console UI is untouched; `/stats full` already shows `byProject`.
