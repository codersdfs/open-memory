# ADR-0024: Real-time benchmark — open loop, with recursive churn

- **Status:** Accepted (2026-10-19). `scripts/realtime-bench.mjs` + `src/bench/realtime.ts` + `tests/realtime.test.ts`.
- **Options:** keep two offline benchmarks (LoCoMo accuracy, scale-bench cost) vs **a third one that measures a live mixed workload** (chosen) vs a UI dashboard over the same numbers vs replaying a recorded traffic trace.
- **Why a third bench:** the two existing ones answer "is the answer right?" and "what does a corpus size cost?", both with a quiet process. Neither answers "what does one agent feel while another is writing?" — and the store is shared, so that is the normal case. It also cannot be answered by averaging: an open-loop run that is fast on average and stalls for half a second is a run that drops requests.
- **Open loop, not a for-loop:** requests are scheduled on a fixed clock (`1000 / rate`) whether or not the previous one finished. In-flight work is bounded by `--workers`; a request that cannot be issued is counted as `dropped`, never silently retried. A closed loop would report the latency of a client that politely waits, and queueing — the number a caller actually feels — would never appear.
- **Quality under churn, measured by a marker:** each seeded fact carries a unique rare token (`zq1042`), and a search counts as a hit when that token comes back in the top `k`. A `k`-capped list is scored, so this is recall@k, not "did it return anything". Live writes keep arriving during the run, so the recall figure belongs to a store that is moving, not to a frozen fixture. Per-mode breakdown (`bare` / `noisy` / `cjk`) is reported separately because pooling hides script-specific regressions (verified: the hash embedder loses a fifth of CJK markers while the pooled number stays above 0.9).
- **Recursive churn:** a separate timer rewrites one section of one vault page and calls `syncKnowledge`, so the knowledge index is being re-indexed while searches run. Sync is not a per-request operation, so giving it its own clock is more honest than mixing it into the request mix.
- **One process, the production stack:** `MemoryService` + `SqliteVectorStore` on a temporary file, hash embedder by default (no key, no network, reproducible), `--embedder nim` to opt into the real 2048-dim provider. No HTTP layer by default: the number is the engine's, and HTTP overhead would be this harness's opinion about `node:http`.
- **Gates, not adjectives:** `--assert` fails a run on errors, drops, `search p95` over a threshold, recall@5 under a floor, a budget overrun, or a sync error. The per-second series is part of every report because the average cannot see a stall.

## Consequences

- The report is `bench/results/realtime-<tag>.json` (`schema: realtime-bench/1`); stdout is one JSON line per run, stderr is the live per-second line plus the human table, so a curve is `for r in 20 40 60 80; do node scripts/realtime-bench.mjs --rate $r; done`.
- Measured on this machine (Node 24.11.1, Windows, hash/384d, 800 seeded facts, 6 projects, 12 vault pages): 20-80 req/s sustain with zero drops and `search p50 ≈ 10 ms`; the knee is between 80 and 100 req/s, where the queue shows up first in writes (`p50 52 ms`) and drops appear at ~4% of the offered load. Sync's p95 reaches 1.5 s at saturation because it competes with the same event loop.
- The CJK recall loss is a property of the default hash embedder, not of the term index: bare-marker queries hit 100% on the same corpus, so the row and its posting are there. Any published recall number from this harness must name the embedder.
- `src/bench/realtime.ts` is pure (percentiles, buckets, summariser, seeded corpus) and unit-tested (`tests/realtime.test.ts`, 13 cases); the driver stays a script. The same split as `scripts/scale-bench.mjs`.
- Limits: one process, one core, synthetic corpus, warm page cache, temp DB on local disk, no HTTP, no reader/judge tokens. It measures the memory system's own latency and recall — not the quality of an answer an LLM builds from them.
