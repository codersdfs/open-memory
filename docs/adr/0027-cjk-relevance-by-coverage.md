# ADR-0027: Chinese search recovers by coverage, not by better tokens

- **Status:** Accepted (2026-10-22). Changes `src/core/retrieval/terms.ts` (new), `bm25.ts`, `hybrid.ts`, `src/core/store/{sqlite,memory}.ts`.
- **Problem:** on the real-time bench (`scripts/realtime-bench.mjs`, hash embeddings, threshold 0.35), CJK queries scored recall@5 **0.6484** against 1.0 for bare and noisy English, and **64 of 182** Chinese queries returned nothing at all. The product reads as broken in the language half its own queries are written in.
- **Diagnosis — the tokens were never the problem.** `bm25.ts` already segments CJK into unigrams and bigrams, so 「用户喜欢简洁的回复」 was indexed correctly. The failure was the *denominator*: `bm25Score` normalised by "the score a document holding every query term would get", and a Chinese question expands one topic word into three terms (「配置」 → 配 / 配置 / 置). A row holding the gold marker plus the topic word verbatim earned **2 of 3** shares, so the gold row scored bm25 **0.135** and unrelated rows that merely shared the question's grammar scored **0.127** — 0.008 apart, which no threshold can separate. Fixing the denominator raised gold to 0.524 but the noise to 0.489: still inseparable.
- **Why more stopwords cannot fix it.** The filler in a Chinese partition is not function words — it is *shared subject matter*. Nine of ten rows in a project say 「项目 <project> 的约定」, so those words have a high `df` and a real `tf`, and any BM25 variant that rewards either will rank them. The signal was never in the corpus statistics; it is in "does this row hold the thing that was asked for".
- **Decision (1): the index and the query share one term vocabulary.** `terms.ts` wraps `tokenize` with a function-word filter — CJK single characters (的 / 是 / 在 …), CJK bigrams (什么 / 怎么 / 可以 …), the straddle bigrams a `n-gram` split produces across a word boundary (么配 / 置的), and 43 closed-class Latin words. It guarantees `indexTerms(text) ⊆ queryTerms(text)`: a filter that keeps a term on one side only silently prices queries out of the corpus. The inverted index (`memory_terms`, `term_df`) is built from `indexTerms`, so `df` no longer counts postings for 「的」. Before this, a Chinese question produced ~40 postings and the eight rarest were mostly filler, which is what crowded gold rows out of the shortlist.
- **Decision (2): `Bm25CorpusStats.queryTerms` sets the scale.** The numerator still uses every expanded term, so a row matching more of the expansion still ranks higher; only the denominator switches to the terms actually asked. A verbatim match lands at 1.0, not 0.67.
- **Decision (3): relevance is ordered by coverage.** New `coverage(text, query)` in `terms.ts` is the share of the query's asked-for words that the row holds, with a matched two-character word counting once (its halves are the same word) and the same bar as the row holding only 「的」 and 「置」. `searchOne` computes it per candidate and uses it three times:
  - **Gate:** `coverageScore >= 0.75` is an additional way past the relevance filter, independent of `threshold`. An explicit `threshold` stays the caller's number and is not re-tuned by this ADR.
  - **Rank:** sort is `coverage DESC, score DESC, id` — coverage leads, because recency and reinforcement otherwise lift a row holding one asked-for word above the row holding three.
  - **Stage 2:** MMR and `budgetEnforce` receive `coverage + score / 2` as their relevance value (both inputs are in 0..1 and the score is bounded by 1.0, so this orders by coverage first and never lets diversity or the budget undo it). MMR's ordering is preserved; no re-sort was reintroduced.
- **Why rank by coverage rather than filter harder.** Tightening `threshold` to admit only the gold row also admits less: recall@1 and recall@5 move together, and the bench's noisy mode already sits at 1.0. Ordering decouples them — every candidate that clears the gate is still returned when `k` allows, it is simply no longer outranked by a row with an older timestamp.
- **Measured result** (`node scripts/realtime-bench.mjs --duration 20 --rate 60`, 3 runs, hash embedder, same seed): CJK recall@5 **0.648 → 1.0**, recall@1 0.522 → 1.0, empty answers 64 → 0; bare 1.0 → 1.0; noisy 1.0 → 1.0 (recall@1 0.95–0.99, mrr 0.99); overall recall@5 0.8815 → 1.0; throughput 60.15 op/s, 0 errors, 0 dropped, search p95 9–10 ms — unchanged. Also holds with `MEMORY_ASSEMBLE=off` and with `MEMORY_Q8=on`.
- **Cost, measured:** `coverage` is one predicate per candidate, so `hybrid` gained no I/O. On the 4000-row × 384-dim scale bench `search` p50 28.6 → 30.4 ms and `lexicalCandidates` p50 4.74 → 5.16 ms — inside run-to-run variance for this script, and the 10^5 projection rose 706 → 751 ms against a 700 ms budget line that the script reports without asserting. The store is not touched: the term vocabulary changed what `memory_terms` contains, and `backfillTerms()` rebuilds it on open, so an existing store is migrated by being opened.
- **Cost, not measured:** `coverage` scores the *stored text*, not the projected fragment the caller receives. A row that holds the marker on line 40 and repeats the query's words on line 2 here counts as a top hit. That is the same blind spot `bm25Score` has always had, and fixing it means re-running the term pass after projection.
- **Rejected (measured, not argued):** using the hash embedder's own cosine to rescue Chinese. Probed pairs scored "TypeScript engineer hates boilerplate" vs 「TypeScript 工程师 讨厌 样板代码」 at **0.783**, 「用户喜欢简洁的回复」 vs "user prefers concise replies" at **-0.013**, and 「部署流程使用 k8s」 vs "the deployment pipeline uses kubernetes" at **-0.377** — the hash vector is character noise on this axis and cannot be a signal in either direction. `weights.vector` stays 0 for `hash`, which is also why the relevance gate must not require a vector score.
- **Rejected:** an `Intl.Segmenter` dictionary pass. It needs no dependency and would segment better, but the diagnosis above shows segmentation was never the bottleneck, and it would change the index vocabulary for every existing row without a measured gain.

## Consequences

- `tests/terms.test.ts` (14) pins the `indexTerms ⊆ queryTerms` invariant, the stop lists, and `coverage`'s two behaviours that matter: a held two-character word counts once, and a held function character counts zero.
- `tests/relevance.test.ts` gains two cases written in Chinese — the marker outranks a grammatically identical row with a different marker, and a Chinese question still returns the partition's only useful row. The first **fails on the pre-ADR code** (verified by stashing the retrieval diff) and passes after; before this, every relevance case in the repo was English, which is how the regression lived in a green suite.
- `tests/setup.ts` now clears `MEMORY_Q8`, `MEMORY_ASSEMBLE` and `MEMORY_RECONCILE_NEIGHBOURS`: a shell that exported one of them flipped the colour of the relevance tests without touching a line of code.
- Full suite: 44 files, **551 passed, 7 skipped** (was 545 / 7).
- The bench's `minRecall5Cjk` gate (0.6) is left at 0.6. It is now cleared by a wide margin, and raising it to what the code achieves would turn a regression detector into a ratchet.
- Known limit, unchanged by this ADR: CJK v0 has no dictionary, so 「数据库迁移」 is indexed as 数据 / 据库 / 迁移 and a query for 「迁移数据库」 shares only 「迁移」. Coverage makes the row that holds the query's words win; it does not make 「据库」 mean anything to someone asking about 「数据库」.
