# ADR-0049: The principal and the local boundary

Date: 2026-11-09

Status: Accepted

Implements P7 of the memory-systems research plan (`docs/research/memory-systems-notes-2026-11-07.md` §3, review verdict: approved, with the review's explicit reservation that the at-rest-encryption half of gap2 is *drawn as a boundary, not solved* — quoted in full in "What this does not do"). Stands on ADR-0007 (the namespace is `{agentId, userId}` and the read fan-out is the contract this boundary guards), ADR-0038/0039 (`all` is a question about the store, filtered by user), and the plan's own prior half-steps: ADR-0010 (the console is the only writer of credentials) and the loopback + Origin mutation gate this adds a third tier to. Related: ADR-0042 (the project marker's user segment, now server-owned), ADR-0043 (the console agent routes, gated with everything else).

## Context

gap2, in the research notes' own audit: **isolation was name-based and unauthenticated**. Identity was whatever the caller reported — `AI_MEMORY_USER`, or any namespace string at all — and the HTTP surface's only defenses were the loopback bind and the Origin tier, neither of which sees a body. Any process on the machine that could reach the port could read another user's partitions by saying so, and the README admitted the file-mode story was hollow on Windows. The plan's threat-model paragraph is the design brief and is worth quoting because every decision below follows from it: a same-account process can read the key *and* open the SQLite file directly, so no token stops it; a daemon holding a unique secret can only defend *cross*-principal access, never itself; therefore **"single daemon, many principals" is abandoned before it is built**, and the model that ships is one daemon bound to one principal, with a second OS account served by its own store file and its own port.

## Decision 1: one daemon, one principal, one key file

At startup — the `runsAsMain` block of `src/api/server.ts`, the code `ai-memory daemon restart` execs and `npm start` runs — the daemon loads or creates `principal.key` in the memory home (`resolveHome()`, default `~/.ai-memory/`, `AI_MEMORY_HOME`-overridable). The file is JSON: `version`, `token` (256 bits of `randomBytes`, base64url), `user` (the namespace user segment this principal owns), `createdAt`. It is written tmp → explicit `chmod 0o600` → rename, because `writeFile`'s own mode is masked by the umask — the same discipline the `.env` writer uses (`src/core/envFile.ts:182-184`).

**The Windows fact, stated plainly and replacing the old 0600 claim in the README:** POSIX mode does not exist on Windows. Node's `chmod` has no permission bits to set there and the call is a no-op; what scopes the file is the ACL it inherits from its directory, which by default is the user profile (`os.homedir()`), the same inheritance `%APPDATA%` relies on. That is the protection — an account-scoped inherited ACL — and it is what makes the token able to defend the one thing it defends: another OS account's process can reach the loopback port but cannot read this account's key file, so it cannot mint the header. That sentence is load-bearing and was nearly falsified by this ADR's own first cut: the daemon briefly injected the token into the HTML pages it served (Decision 4 records the rejection), which handed the header to any process that could issue one unauthenticated GET. The invariant the design now holds to is stated once and enforced everywhere: **the daemon serves the token to nobody** — it exists in the key file on disk, in wire clients that read that file under the owning account, and in a browser that the operator pasted it into.

The `user` segment is frozen in the file at creation (resolved the way writes have always resolved it: `resolveUser` — explicit → env → OS username), so a later environment change cannot move the identity. After creation, **the file, not the ambient env, is who the daemon is**.

The gate lives at that entry and nowhere else. `buildServer` accepts `principal` explicitly; `undefined` builds the ungated server the test suite and library embedders have always built. That is deliberate, not laziness: a gate over a token nobody holds is a 401 generator, not a boundary — the boundary exists where the key file does, and the daemon main block is the only place those two meet. Every gated route's 401 error names the header and the key file path, so a stranger's curl explains the whole scheme in one line.

## Decision 2: the wire — `x-ai-memory-principal`, 401 then 403

Every read/write route demands the token in the `x-ai-memory-principal` header (named here once; the constant is `PRINCIPAL_HEADER` in `src/core/principal.ts`, and clients import it rather than re-spelling the string). Comparison is `timingSafeEqual`. No token is **401**; a token that is not this daemon's is **403** — the distinction an operator acts on (the client never read a key file vs. a foreign principal is knocking).

What stays open, and why:

- **`/health`** — the liveness probe the CLI's daemon-vs-in-process decision and `daemon restart`'s poll both depend on; it names no partition and holds no store data.
- **The static shell** (`/`, `/app/*`, assets, the vault graph page) — for safe methods only. Those are code and markup, not store data, and they carry **no secret** (Decision 4's rejected injection is why this clause is worded as an invariant rather than an implementation note): an unauthenticated GET of any served page yields nothing that mints a header. Everything dotted is exempt except the four id-bearing data prefixes (`/memories/`, `/sessions/`, `/knowledge/`, `/projects/`), spelled out so a session id or a slug that happens to contain a dot never reads as a static file.

Every mutation is gated unconditionally. `POST /admin/shutdown` keeps its non-loopback 404 pre-check and gains the token requirement — a loopback process on another account can no longer shut down a daemon it cannot authenticate to — with one exception that exists to keep the break-glass walkable (Decision 6): a shutdown request carrying the key file's *current* token is accepted even when the running daemon holds an older binding, because only the owning account can have read that file.

## Decision 3: the user segment is server-owned

This is the "overwrite" in the plan's sentence, and it has two arms, because the two cases are not symmetric:

- **Unpinned scope resolves with the principal.** A write carrying `agent`/`scope` and no `namespace` lands in `<agent>:<principal-user>` — resolved from the file, never from what the caller's environment says. The same pinning drives the server-resolved read fan-out: `agent`/`scope` searches and `all` sweeps resolve their partitions with the principal's segment (an `all` sweep enumerates the store and filters by it, exactly as ADR-0038 already filtered by user). `POST /projects`' `user` field is overridden the same way — the project marker row lands in the principal's shared layer regardless of the body.
- **A pinned foreign segment is refused with 403.** An explicit `namespace` (or a `namespaces` list entry, or an `/extract` namespace, or a `/stats`/list query param) naming a user segment the principal does not own is not honored and not silently relabeled: an explicit partition name is a promise about where a row lives, and a daemon that quietly rewrote it would answer a question the caller did not ask and scatter writes somewhere they cannot be found. The 403 names the segment, the principal's own, and the recover command.

Two doors are always in bounds: the principal's own segment, and the legacy `default:default` — the one namespace that is nobody's segment and everybody's, which every read fan-out already covers and where every pre-scoping row lives. Exempting exactly it is what makes the plan's "namespace text unchanged, existing rows readable" true: **no namespace in the store is rewritten, no migration runs**, and every row filed under the principal's segment or in the legacy partition reads back exactly as before. Rows under some other historical segment become unreachable over the wire — that is the boundary working, and `principal recover` (Decision 6) is the re-binding tool for the machine-move case.

The boundary follows by-id access too: `GET`/`PATCH`/`DELETE /memories/:id` and `/memories/:id/supersede` check the row's own partition (an id is an address, and the segment it resolves to is checked like any other). `/namespaces` — the console's picker — filters to partitions the principal can actually open, because a picker advertising partitions every request to which will 403 is noise plus a directory of other segments.

## Decision 4: how each caller carries the token

- **CLI and MCP** — `MemoryClient` (`src/cli/http.ts`) reads the key file once per instance, lazily, and attaches the header to every call, including the `POST /admin/shutdown` that `daemon restart` sends. The MCP stdio server proxies through that client when a daemon answers, so every `memory_*` tool rides the same token. A missing file means no header and the daemon's 401 names the path — the client never guesses.
- **The hook** (`src/adapters/inject.ts`) — this is where honesty beat tidiness: the hook **never spoke HTTP**. `inject` has always opened the store in-process (`buildInjection` → `new MemoryService`); its `server:` option existed as a dead seam. There was no request to attach a token to, and probing a daemon the caller never named would make every hook's behaviour depend on whatever happens to listen on :3000. What shipped: the seam became live — `ai-memory inject --server <url>` now goes to the daemon first (health + version probe, then brief/search over the same wire as the CLI, token included via `MemoryClient`), and falls back to the in-process store on any refusal or error, the hook's never-break-the-turn contract intact. Default hooks (no `--server`) behave byte-for-byte as before; their boundary is the OS account they run under, which is the threat model's declared floor.
- **The console** (`ui/`) — the browser cannot read a key file, and the daemon gives it nothing: the first cut of this ADR injected the token into the served HTML (`<meta name="ai-memory-principal">` in the console shell and the vault graph page), and independent review killed it with one request — an **unauthenticated** `GET /graph.html` returned the live token in the body, so a process under another OS account, the exact threat Decision 1's sentence claims to stop, could mint the header without ever touching the key file. The reasoning that allowed it ("same-origin only — this server sends no CORS headers") defended against *browser* pages and was blind to *processes*: CORS is a browser mechanism, and the threat model's attacker is curl. There is no delivery channel narrower than the port itself, so the console now authenticates like every other client: a gated daemon answers the console's first call with 401, the console shows a credential gate (`ui/src/components/PrincipalGate.tsx`), the operator pastes the token once (`ai-memory principal reveal` prints it; the console stores it in localStorage for this origin and never renders it from the server side), and the vault graph page shares the same origin-scoped storage and grows the same unlock form. An ungated server never shows a gate, and nothing the daemon serves to an unauthenticated reader contains the token — pinned by test, because it is the invariant the whole ADR stands on.
- **The benches** — `bench/evhit.mjs` spawns the real daemon entry, so it points `AI_MEMORY_HOME` at its own tmp dir (it must never create a key in the operator's real home) and reads the token back from that file; `bench/run-locomo.mjs` reads the token from the memory home for its `OM_BASE` daemon. Both also stopped pinning explicit `locomo:<sample>` namespaces — a foreign segment the moment a principal exists — and name the **agent** layer instead (`locomo`, `locomo-<sampleId>`), letting the daemon pin the segment; that is the P7-native form and it is how wire callers should address partitions now.

## Decision 5: multi-account machines — separate stores, separate ports, explicit export

One daemon serves one principal. A second OS account on the machine gets its own store file and its own port: the store path is already per-account by default (`resolveDbPath` → `os.homedir()`), and `dbPath.ts`'s precedence (`--db` → `MEMORY_DB_PATH` → `AI_MEMORY_DB` → home) plus the `PORT` variable are the documented knobs — a second account sets `PORT` explicitly, because a default port is shared by design. There is no principal switch, no `--as-user`, no multi-principal table: the plan abandons that model because a daemon holding one secret cannot defend what it shares, and a daemon holding many secrets is a server, which is a different product. Sharing a memory across principals is an **explicit export** — the store's own export/import path — never a namespace spelled across the boundary.

## Decision 6: `principal recover --from-db`

The key file is the single point of loss, so the CLI grows `ai-memory principal`:

- **`status`** (default) — the key path, the bound user (token masked to its last four, the console's own rule), and whether the store's partitions agree with the binding. The store read is the widest one (`distinctNamespaces({includeDeleted: true})`); a mismatch names the segments it found and prints the recover command.
- **`recover --from-db`** — the lost-key and machine-move path. One-way by construction, and honest about what it does not do: the lost token is never reconstructed — nothing in the store can produce random bytes it never saw — so recover writes a **new** token and re-derives the `user` from the partitions the store actually holds. The derivation is a frequency vote over the user segments of every partition, the legacy `default:default` excluded because it says nothing about who owns anything (a store holding only legacy rows recovers as `default`, which keeps exactly those rows readable). Existing rows stay readable because the segment they were filed under is precisely what gets re-bound. The output names the overwritten user, tells every client holding the old token that they 403 until they re-read the file, and — when a daemon answers `/health` — says that the running process still holds the previous binding, before the restart command. The restart itself is where this flow used to die: the shutdown request carries the file's *new* token, the running daemon compares it against its *old* binding and 403s, and the operator is left with a daemon no documented command can stop. The gate therefore keeps one repair lever: on a mismatch the daemon re-reads the key file, and a caller presenting the file's *current* token may pass `/admin/shutdown` (only the owning account could have read it — the boundary holds) while every other route answers 403 with the one message that names the way out, `the key file has been re-issued since this daemon started — restart it`, because a new-token request served by the old binding would be enforced under the old user segment. `daemon restart`'s own 403 failure names the same exit in case the two sides read different homes.
- **`reveal`** — prints the raw token. The CLI runs on the owning account, so this is the honest form of `cat principal.key`; it exists because the console's unlock gate needs something to name that is not a file path.

## Cost

- **Per request:** one header read and one constant-time compare; the namespace checks on the write path are the string parse the fan-out was already doing. No new dependency (the whole module is `node:crypto`, `node:fs`, `node:path`).
- **Per daemon:** one file read at start; one file write ever.
- **Surface:** one new core module (`src/core/principal.ts`), one new CLI verb with three subcommands (`src/cli/principal.ts`), one header, one file, one console gate component. No schema change — the store, its tables and every namespace string are untouched.
- **Behavioural narrowing, on purpose:** an explicit `--namespace some:user` (or `AI_MEMORY_USER=other` over the daemon) naming a segment the principal does not own now answers 403 where it used to be honored. That is the gap being closed; the error message says so and names recover. Aggregate read routes that were never namespace-addressed (`/projects` list, `/knowledge/sync`, `/graph`, `/positions`, `/sessions`) are token-gated but not segment-filtered — they read the one store this principal owns, which is the same reach the file already grants.

## What this does not do

The threat model, stated at the width the plan set and no wider:

- **A process under the same OS account is not defended.** It can read the key file, and it can open `memory.db` with any SQLite tool — a token in front of the HTTP port cannot beat either. The plan's own words: any token is powerless there; the boundary's honest claim is only *cross*-account, and the in-process paths (CLI fallback, hooks, the MCP server without a daemon) all live on this side of the line by design.
- **No at-rest encryption.** The store is plaintext SQLite and stays that way: a zero-dependency SQLCipher equivalent does not exist in `node:sqlite`, and the review's missing-items note says exactly what this ADR must repeat — *"gap2 的 at-rest 加密一半仍未真正关闭（P7 明文宣布不做，只把边界写进 ADR/README）"*; the audit's "no at-rest encryption" is a drawn boundary, not a solved gap. What changed on that front is the honest README wording about what the file modes do and do not mean on each platform.
- **No multi-principal daemon, no principal rotation schedule, no token revocation list** — the file is the identity, recover is the break-glass, and a second account is a second store.
- **The DNS-rebinding shape is unchanged.** A page that can make this origin's browser treat itself as same-origin could read what it could always read; that is a browser-boundary problem the Origin tier partially covers for mutations and no P7 decision widens or narrows.

## Consequences

- `tests/principal.test.ts` pins, on a gated in-memory server: tokenless 401 naming the header and key path (read *and* write *and* `/admin/shutdown`, which is proven not to fire); wrong-token 403; foreign explicit namespace 403 on writes, on a `namespaces` list (one foreign entry refuses the whole read), on `/stats`/list/`/extract`, and on by-id `GET`/`PATCH`/`DELETE` with the refused delete proven not to have deleted; same-principal passthrough byte for byte; the env overwrite (`AI_MEMORY_USER=somebodyelse` in the caller's environment cannot move a scoped write off `pi:frank`); the legacy `default:default` partition open both ways; the picker filtered; **the static shell open and carrying no secret** — `GET /graph.html` answered tokenless contains neither the token nor the tag, and the review's own repro is pinned as a pair: the unauthenticated page fetch yields nothing, the gated route still 401s; and, on an ungated server, the exact pre-P7 contract — any explicit namespace accepted, the picker unfiltered. Client tests: `MemoryClient` with a temp-home key file gets through, without one surfaces the 401; the hook's `--server` path rides the token and degrades to the in-process store on a dead daemon. Repair-lever tests: with the key file re-issued under a running daemon, `/admin/shutdown` with the file's current token is accepted and the shutdown fires, every other route answers the `re-issued` 403 naming `daemon restart`, and a token that is neither the binding nor the file stays a plain mismatch. Recover tests: the segment derivation unit (frequency vote, legacy excluded, `default` fallback); recover over a real temp SQLite store re-binds `frank` and writes a token different from the one it overwrote, with and without a pre-existing (wrong) key file; refuse without `--from-db` and with no store; `status` naming a mismatch; `reveal` printing the raw token; the POSIX 0600 assertion (on Windows the test asserts the file's existence and documents that there is no mode to assert — the honest check this platform allows).
- The real-daemon smoke run in the landing session (one-shot script, deleted after): fresh temp home, spawned entry — `/health` open, tokenless read 401, wrong token 403, `agent` write landing in `pi:frank`, foreign namespace 403, own namespace 201 passthrough, legacy list 200; the key file created in the data dir the daemon was pointed at. Re-run after the review fix with the leak probe added: the tokenless `GET /graph.html` body contains no token, and the gated route stays 401 without credentials.
- A stale daemon from before this change serves ungated as it always did; the CLI's version gate already routes clients away from it. A new daemon against an old store needs nothing: the store has no principal state, the key file is created on first start, and every pre-existing partition under the OS user segment is in bounds immediately.
- The README's API table and its curl example now show the header; the `0600` sentence in the Embeddings section is replaced by the platform-accurate one (POSIX mode via explicit chmod; on Windows the profile-inherited ACL and nothing else).

## What would change the verdict

A real multi-principal demand from the field — one user legitimately needing two identities against one store over the wire — would reopen Decision 5, and the answer then is a second daemon on a second port against the same file only if SQLite's locking story is re-measured, not a principal table. A zero-dependency at-rest story inside `node:sqlite` (a codec or SEE-equivalent landing upstream) would close the review's reservation and should retire the "not defended" paragraph's second bullet the day it exists. And if the console ever needs to run from a genuinely foreign origin (a hosted console), the paste-once localStorage gate is the assumption that breaks first — the token would be sitting in a browser whose origin the user does not control, and that is a real credential surface (per-user server-side sessions), a different ADR.
