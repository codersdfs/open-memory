# ADR-0009: The embedding switch is settings-plus-restart, never a live swap

- **Status:** Accepted (ticket 015, 2026-10-11).
- **Options:** (a) **a non-secret settings file the console writes, taking effect on the next start** (chosen); (b) hot-swap the running `MemoryService.embedder` and let searches use the new provider immediately, mid-migration; (c) read-only: the console displays the active provider and a copyable command, and changes nothing.
- **Context:** The provider is `createEmbeddingProvider(env)` over `EMBEDDING_PROVIDER` and friends (`src/core/embedding/index.ts:24-58`), resolved once at construction and then frozen for the life of the process (`src/core/memoryService.ts:29`, used at `:79`, `:127`, `retrieval/hybrid.ts:204`), with no reload — `src/config.ts` reads `.env` exactly once. Vector width is load-bearing: the store keeps raw JSON vectors, so a swap invalidates every one of them, which is why `reembedAll` exists and rewrites every row in every partition (`src/core/embedding/reembed.ts:29-108`). A whole-store mismatch is already loud: `MemoryService.init()` refuses to serve a store whose vectors do not match, naming both dims (`src/core/memoryService.ts:47-53`). But that guard reads `storedDim()`, which is `SELECT embedding … LIMIT 1` (`src/core/store/sqlite.ts:218-232`) — and its own comment concedes the hole: "A half-migrated store reports whichever row lands first." Past the first row nothing is guarded, and a foreign-width row is **skipped, not fatal** (`sqlite.ts:369`, `:221`, `:299`), so a partly-migrated store answers with quietly fewer rows. The worst instance is not a corrupt store but a window: the migration finishes, every row is at the new width, and the still-running process embeds its queries at the old one — searches return nothing at all until it restarts. A silent wrong answer is the expensive kind here, and it is invisible from inside a process that only knows its own configuration.
- **Decision:** the console may **write** the switch; it may not **become** the switch. Non-secret provider settings live in `~/.ai-memory/settings.json`, written atomically, with the real environment winning over the file and the file winning over the built-in default — cheap because the factory already accepts an env object, so the seam is a merge at the two construction sites (`src/core/memoryService.ts:29`, `src/cli/index.ts:225`) rather than new plumbing. Changing the provider therefore requires a restart, and `GET /embedding` exposes `needsRestart` by comparing the live embedder against what the settings would build, so "restart required" is an assertion rather than a sentence. The migration itself runs in-process with the **target** provider (`reembedAll(service.store, target)`), behind a mandatory dry-run that states the row count first, and the order is fixed — **write settings → dry-run → migrate → restart**. Restarting in the middle is refused by `init()` naming both dims, which is the guard working; finishing the migration without restarting leaves the live process reading nothing, which the console states before it is allowed to start and again when it ends. API keys stay in the environment: the console reports whether the variable a provider needs is present, by name, and never stores, transmits or echoes a key.
- **Boundary:** one process, one vector space. No `setEmbedder`, no per-request or per-namespace provider, no key storage, no writing the user's `.env`, no auto-restart. The store's widths are surfaced (`byVectorDim`, `unreadableRows`) precisely so the state this decision allows — mixed widths during and after a partial migration — is visible rather than latent.
- **Cost if wrong:** switching providers costs a restart, which is friction exactly when someone is experimenting with providers — the moment they are most likely to compare two of them. Accepted: the alternative is a window in which every answer is drawn from a vector space the store is only half in, and this store's whole pitch is that its answers are explainable. A `reembed` that must be re-run after an interrupted process is the same trade.
- **Revisit if:** two providers must be live at once (per-namespace vector spaces), or a migration ever becomes resumable — either makes a supervisor that owns the embedder the real shape, and this ADR's restart boundary the thing to replace.
