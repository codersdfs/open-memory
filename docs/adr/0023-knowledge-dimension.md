# ADR-0023: Knowledge is a markdown page, indexed section by section

- **Status:** Accepted (2026-10-19). `memory_knowledge` (MCP), `GET /knowledge`, `GET /knowledge/:id`, `GET /knowledge/:id/neighbors`, `POST /knowledge/sync`, `ai-memory knowledge ls|show|neighbors|sync|link`.
- **Options:** keep markdown as a UI-only vault (`/graph`, ADR-0008 era) vs import pages once into memories as opaque blobs vs **make the page the truth and the rows its index** (chosen).
- **Why the file stays the truth:** knowledge is edited by humans in an editor, reviewed in a diff and linked by hand. If the row were the truth, every edit would need a tool call, and a page copied into another repository would arrive with no history. Instead `vault/` remains an ordinary directory of `.md` files, and `syncKnowledge` reads it.
- **Why not the old one-shot ingest:** `wiki-ingest` wrote each section as an ordinary memory. Three costs showed up: re-running it duplicated rows, an edit could not find the row it replaced, and the row was indistinguishable from a chat sentence, so reconcile could reinforce it away. The old rows are not lost — sync **adopts** them by their `wiki:<page>` + `section:<n>` tags, keeping their ids.
- **Section identity is the heading, not the position:** `sectionKey("How tokens work")` → `how-tokens-work` (CJK keeps its letters; punctuation-only headings fall back to `section-<n>`; repeats get `-2`). Position would make inserting a paragraph rewrite every row below it; a heading lets one edit touch one row, and the sync is idempotent — measured: second sync of unchanged files reports `inserted: 0, updated: 0, unchanged: N, embedCalls: 0`. The database enforces it too: a partial unique index on `(knowledge_id, knowledge_section) WHERE knowledge_id IS NOT NULL AND is_deleted = 0`.
- **Links live beside the rows, never inside retrieval:** `knowledge_links(from_id, to_id, target)` is written per page on sync; `to_id` is `NULL` when the target does not resolve, which is the file's maintenance debt rather than an error. A search result can show its links as metadata, and walking them is an explicit `neighbors` call with a bounded depth (default 1, max 3, cycle-safe). Implicit expansion was rejected: it turns one hit into five pages of context the caller did not ask for, and the cost is paid on every turn.
- **One write path:** `syncKnowledge(deps, opts)` is the only thing that creates or relabels knowledge rows. `wiki-ingest` keeps its docs → vault conversion and then calls sync; the CLI, the MCP tool and the HTTP route all reach the same function. Embeddings are batched — a 300-section vault costs one `embedBatch` call, which is why the report counts `embedCalls`.
- **Ordinary writes cannot touch knowledge rows:** the reconcile neighbour query in `saveDetailed` passes `knowledge: null`, so a chat sentence is never merged into a page section. Symmetrically, decay skips `knowledgeId !== null` rows entirely: their lifetime belongs to the file, and archiving one would hide a page that is still on disk (the next sync would re-insert it and the row would ping-pong).
- **No LLM, no key, no watcher:** same constraint as ADR-0002. Sync is a directory read plus heading splits; nothing summarises a page, and no filesystem watcher is installed — syncing is a command the operator (or the agent, via `memory_knowledge op=sync`) runs.
- **Default partition is `shared:<user>`:** knowledge is meant to be read by every agent the user runs, unlike a private chat note.

## Consequences

- Schema: `memories.knowledge_id`, `memories.knowledge_section`, plus `knowledge_links`; migration is additive (`PRAGMA table_info` → `ALTER`), so an existing store opens unchanged and legacy `wiki:*` rows are adopted on the first sync.
- `VectorStore.knowledge?` is optional (`KnowledgeCapability`: `listByKnowledge`, `listKnowledgeIds`, `replaceLinks`, `links`), so a third-party store keeps compiling; the read side degrades to "no links" rather than failing.
- Sections are capped at 600 chars of prose (`DEFAULT_MAX_SECTION_CHARS = 1500` at render time, prose clamped at a sentence boundary), 12 sections per page, and prose under 40 chars is dropped: a heading with one line under it is a table of contents, not knowledge.
- Tests: `tests/knowledge.test.ts` (19) pins heading identity, idempotence, single-section edit/delete, whole-page removal, every link spelling with a dangling edge, neighbour depth with a cycle, the `knowledge` search filter in both directions, reconcile isolation, decay isolation, legacy adoption, the four HTTP routes (including the 404 wording) and the CLI round trip. Full suite: 40 files, 500 passed.
- Known limit: the index is a full partition read per sync (`list({limit: 100_000})`), which is fine for a vault of pages and would not be for a million rows; a page renamed on disk is a delete plus an insert, not a move, because the id is the file path (or frontmatter `slug:`).
